# Changelog

Every PR whose title or branch carries a `card#NNNN` token owes a line-initial
`- **card#NNNN** — …` bullet under `## [Unreleased]`, **in the same PR**. A PR that names no
card owes nothing. `docs/PLAN.md § 4` owns that rule and the reasoning behind it, including
why the bullet must be line-initial; `docs/VERSIONING.md` owns when a release collects these
entries and retitles the section.

⛔ **Enforced since 2026-08-30 by `bin/release-pr-guard.py` R4**, on every PR — for seven days
before that it was prose, and six cards' work merged with no entry at all. The two cases that
owe nothing are a PR into `main` (the release retitles this section) and a PR that REMOVES a
card's bullet (a revert of unreleased work); both are argued in that file's docstring. **R5**
holds this file's SIZE under `1 MiB − the bytes it grew in the last 14 days`, so it reds while
there is still time to archive released sections rather than after the contents API has begun
returning it empty. **R6** (card#9707) gives this section a third reader: on a release PR it
compares the cards bulleted here on `dev` against the head's changelog, so a release cannot
quietly ship with fewer cards than `dev` holds. **R7** (card#9814) refuses a release PR whose
copy of this file carries more than two released sections, and so enforces the archiving below.

Sections are newest-first: `[Unreleased]` collects what has landed on `dev` since the last
release, and a release retitles it (`docs/VERSIONING.md § Release flow` step 4).

This file holds `[Unreleased]` and the latest released section only. Every older release is one
file per tag under [`docs/changelog/`](changelog/) — `ls docs/changelog/` lists them — moved there
verbatim by release flow step 13 (`docs/VERSIONING.md`), which R7 enforces. R5 gates this file's
size; `docs/PLAN.md § 4` says why the archive files need no gate of their own beyond R7's backstop.

- **card#12705** — **Agents and subagents leaving a floor wait at the elevator for up to 30 seconds, stand apart while several wait, all board together one at a time when the doors open, and the doors open and close at half their former speed.** The operator asked on 2026-10-31 for a random wait between 0 and 30 seconds (it was up to a minute), for waiting walkers to keep some space between each other instead of standing on one spot, for everyone waiting to go in one at a time before the doors close, and for the doors to move at about half their speed. The doors take a second to open and a second to close (they took half a second); the step through them is unchanged, and the elevator ride the viewer takes is unchanged. Before this change each walker waited its own draw of up to a minute on the doorway itself, two waiting walkers were drawn on one point, and the doors opened for each walker's own wait. (`docs/design/FLOOR.md` § 6.2's walk note items 5, 9, 10 and 14, § 12's *Elevator wait*, *Elevator leaves* and *Queue spacing*, § 13 row 99.)

- **card#12571** — **The installer's informational `ancestry` line reads `UNVERIFIED`, never `FAIL`, when a flusher cron or launchd did not start holds the lock.** After a run that changed anything, `node fleet-reporter/install.js` reports who started the flusher; a Claude Code hook often restarts it first, and the line then reads `UNVERIFIED: the lock holder's parents include no flock and no cron: … so cron's line is NOT verified (informational; the install's verdict does not read it)` on Linux, the same ending on macOS for a pid `launchctl print` does not report, and for a lock no live flusher holds. `PASS` is unchanged for a flusher cron or launchd started. What the step checks and the run's verdict, which reads selftest, health and arrival, are unchanged. The installer changes and the reporter does not, so no reporter version or `fleet-reporter/UPDATES.md` row comes with it. **Upgrade:** pull the checkout; the next `node fleet-reporter/install.js` prints the new line. `fleet-reporter/INSTALL.md` § The checks and D6 § 7 (R-lin-1, R-mac-2) describe it.
- **card#12514** — **The installer's `arrival` check judges only what happens during the run: a re-check or an upgrade on a seat that once had a batch refused passes once a batch is accepted, and a seat whose batches stopped going through no longer passes on batches accepted before the run.** Before its first step, `node fleet-reporter/install.js` reads each site's `batches_ok` in the flusher's `state.json` and the lines of each `REJECTED.<site>.txt`. `arrival` reports `events arrive` (`rc=0`) when a site's count rises during the run, fails (`rc=1`) for a refusal line added since, naming its time, status and code, and reports `NOT ARRIVED` (`rc=2`) naming the count at the start and now when no batch is accepted within its 150 s wait; a running flusher sends each site a heartbeat batch every minute, so a seat with no events still arrives. Older refusal lines are reported as `from before this run, not judged`, and the file is left as it is, the seat's record of every refusal. Before, any line in the file, even one from days earlier, failed every later run with `a batch was REFUSED`, and any batch ever accepted passed. A `state.json` that cannot be read at the start is named, and the site judged by its total. `node install.js arrival` run alone judges what is written while it runs. The installer's own check changes and the reporter does not, so no reporter version or `fleet-reporter/UPDATES.md` row comes with it. **Upgrade:** pull the checkout and re-run `node fleet-reporter/install.js`. `fleet-reporter/INSTALL.md` § The checks, `fleet-reporter/AGENT-INSTALL.md`'s table and D6 § 7 (R-all-23, R-all-24) describe it.

- **card#12571** — **The reporter installs on Linux, Windows and macOS with one command, and the user answers one question.** Asked *"Install the Mezzanine reporter from https://github.com/PupFuzz/mezzanine"*, a seat's Claude Code agent follows `fleet-reporter/AGENT-INSTALL.md`: it proposes the install id and seat id, asks where the user saved or copied the token file from the Seat tokens page, and runs `node fleet-reporter/install.js --token-file <path>` in the background. `install.js` is one node file, the only implementation of every step: the token file (v1, the bare token, or v2, four `<key> <value>` lines carrying the site and the identity) taken into the owner-only config directory, with a warning when another account could have read it, and removed once the config holds it; the config written through the checkout's own reporter rules; the hooks wired after the user's own by a parsed comparison, so a Windows seat's quoted forward-slash entries stay byte-equal; the to-do tools key and the board declaration as before; and the supervised start — the Linux crontab block byte-identical to the one `install.sh` wrote, a user `launchd` agent on macOS for a GUI login (an SSH-only Mac is refused by name), and on Windows no supervisor and one flusher started by the installer.
