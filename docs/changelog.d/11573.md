- **card#11573** — **An event the fold cannot apply is always set aside, and the fold carries on, even when the step that failed is the seat's own state update.** The fold sets aside an event that fails twice (D2 § 6.5's poison-event rule): it counts `fold_error`, badges the seat `derivation_error`, records a transition row and moves past the event. Setting it aside re-ran the seat's state update with that same event, so when the failure came from that update's own write, setting it aside failed as well. The error then stopped the whole fold pass, the event was neither applied nor set aside, and because that seat stayed the furthest behind, every later pass stopped at it the same way, leaving the other seats in its pass unfolded too. Setting an event aside now writes nothing taken from that event and runs the seat's state update without it, so a seat's activity columns and its applied `seq` mark stay those of the last event that applied. If that update fails too, it is undone on its own, the new per-seat counter `fold_quarantine_recompute_error` counts it, the server log carries the error, and the event is still set aside without its transition row; the badge appears at the seat's next state update that succeeds. Separately, a field refused for its format (`format_refused.<field>`) on an event that applied at its second attempt is now counted once; it used to be counted zero times. D2 § 7.2 lists the new counter, and its S30 row names the console-URL counter by its current name, `format_refused.console_url`.
